# Daun HR — Agent instructions

## Scope and authority
Current phase: Phase 0 governance, product feature development on HOLD until owner approval. Documentation and read-only audits allowed; security implementation, new features, runtime/config changes, purchases, production deployment and merge require explicit approval. Existing hris-web auto-deploy is explicitly owner-approved for DEVELOPMENT only, even if hostname looks production. Preserve workflow unchanged unless separately authorized, disclose that PR open/update or push to main may trigger dev deployment. Do not treat domain or NODE_ENV alone as environment authority. Never deploy to real production or use real employee data before launch approval. If central rules unavailable or ambiguous, stop risky actions and report.
Canonical policy: [backend infrastructure and governance](https://github.com/Hisyam-Dzaki/Hris-BE/pull/1) (pending owner review); after merge use Hris-BE main docs/governance and docs/infrastructure. Read repo README, nearest AGENTS, project status, relevant ADR/API contract before editing. Owner instruction overrides project defaults; do not silently relax safety controls.
## Engineering
Preserve Go/Gin/PostgreSQL, Next.js/React/TypeScript, Flutter/BLoC/Dio; modular monolith and stateless clients/API, Docker Compose first, K3s later based on measured need. No unnecessary new service, microservice, dependency or infra migration. Tenant boundaries server-enforced; never trust client tenant ID, host or role. Deny by default, least privilege, verify ownership on all CRUD and foreign keys. No secrets in source, logs, tests or prompts. Use synthetic data, safe defaults, private DB, explicit environment config. Never run destructive migration, volume prune, reset, or credential change without approval and recovery plan. Local/S3 storage abstraction, tenant quotas, private access, encrypted off-site backups, restore tests. Bound CPU/RAM/disk/queues/retries, rate limits and budget; never auto-buy VPS. No silent fallbacks that bypass security.
## Working process
Inspect current branch/diff and existing tests before changes; small scoped commits, preserve unrelated work. Coordinate backend contract changes before web/mobile; update contract and consumers together, flag breaking changes. Require regression tests (including negative authorization and cross-tenant access for relevant changes), lint/build and report exact commands/results or blockers. Never fabricate CI, deployment or test results. No auto-merge or force push; PR with change summary, risks, validation and rollback. Update affected docs/status; distinguish implemented, planned and verified. No real production data or live credentials in local/CI.

Run flutter analyze, flutter test and target builds as applicable once code exists; do not claim scaffold builds without verification.
